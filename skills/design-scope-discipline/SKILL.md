# 设计与评审的规模纪律

适用于任何仓库的非平凡设计文档、新抽象、新表、新协议、新迁移波次，以及人工或 LLM code review。

项目根自带设计纪律文件（如 `DESIGN-DISCIPLINE.md`、ADR 约定、review checklist）时，**以项目文件为准**；本规范是缺省底线。

## 写设计

1. **先量规模，再动笔。** 设计文档第一节给出规模表：表数、组件数、配置项、工程师日、发布波次，逐项对比"需求要什么"与"你打算产出什么"。任一维度产出超过需求 3× 且无解释 = 砍。
2. **复用现有模式。** 每个新抽象都必须解释为什么不能复用仓库里已有的同类机制。判定基准是现有同类功能：它没有提供的保证，不要要求新功能达到；它已提供但新功能缺失的，才是合理缺口。
3. **默认关闭的功能不迁移。** 功能默认关闭时，迁移策略 = 不迁移：先部署、再由操作者打开开关，旧路径继续可用；回退 = 关开关 + 重新部署。禁止为默认关闭的功能设计多阶段确认、CAS 切换、单调 marker、全节点 ACK。
4. **默认关闭的功能不做"上线即 GA"。** 不做按日/周累积的 KPI fact 表、watermark、retention、裁决协议。上线后观察 1–2 周，一句 `SELECT ... GROUP BY date` 能回答大部分"是否继续"的问题。
5. **一次只做一个最小可行范围集。** 第一版只覆盖主要路径，其余明确列为非目标。禁止为了"一次做完"强制多个渠道/入口共用一套 admission 或 release 协调层——复杂度按渠道数相乘。
6. **范围外的保证写成"已知约束"。** 例如"v1 崩溃后不补发，用户重新触发"。不为已知约束新建表、协议或中间件来假装提供保证。
7. **涉及事务就声明锁序。** 设计文档显式给出全局加锁顺序；同层按 canonical key 全序；缺省记录只能在不持有其他业务锁的短事务中创建。

## 写评审

1. **轮次有硬上限。** 每份设计/变更最多 7 轮 review；不收敛就升级到人工决策，不继续自动迭代。
2. **每条 gate 对照现有功能。** 先问"现有同类功能有这个保证吗"：没有 → 降级为已知约束，不是 FAIL；有而新功能没有 → FAIL 成立。
3. **基础设施缺失不是设计缺陷。** 缺全局协调、持久化 fence、跨服务 API 时，gate 标为"需要平台级基础设施，不在本次范围"，不连续多轮 FAIL。
4. **后续版本话题不进本次 gate。** 识别出 v2/v3 议题就登记为后续输入，不借一个功能替整个平台补技术债。
5. **每条 gate 必须可证伪。** 必须写出"什么证据能让它 PASS"；写不出来 = 撤销该 gate，禁止"凡是理论上可能出错的边界都要新机制"。
6. **每条意见量化代价。** 标注人日、表数、组件数；代价大于被保护的价值时，降级为已知约束。
7. **review 不改设计意图。** 只检查声明是否可实现、不变量是否成立；不重定义范围、不加新功能、不把产品决策塞进技术 gate。
8. **含分析性文字时另加论证审读。** 评审对象含分析性文字（设计文档、方案、报告正文）时，按同根 [`de-ai-flavor`](../de-ai-flavor/SKILL.md) 的论证审读模式及其 `references/argument-review.md` 检查命题与推理：被反驳的主张是否真的有人提出，限定是否指向真实的对象与条件。纯代码变更不做文风量测，缺这一项不阻塞。同根依赖缺失时，先按本仓 README 把整个仓库克隆到可写工作区再加载，不凭记忆重述方法。

## 例外

功能的核心价值就是被豁免的抽象本身（例如"交付一个分布式事务框架"）时，在设计第一节显式声明"本功能核心价值是 X，因此上述哪几条不适用"并说明理由。附件、上传、工具调用、记忆、压缩、hooks 这类功能不构成例外。
